Universal Prompt: Evolve Existing PTF/Gunda Tool into an Integrated Company Operations Platform

Context

I already have an existing internal tool called PTF / Gunda. The tool is already functional and contains many departments, workflows, data structures, workspaces, onboarding features, workshop features, performance features, FMD/scheduling features, ID generation, logbooks, appearance/uniform management, tasks, employee profiles, reporting, backups, and other functionality.

DO NOT build a new application from scratch.

The existing tool is the foundation. Modify, extend, reorganize, and improve the existing tool while preserving everything that already works.

The long-term goal is to make this tool function as an internal company operations platform that can eventually integrate naturally with the Microsoft environment we already use, including Microsoft company accounts, Microsoft/Entra-style identity and role-based access, SharePoint, Power Apps, Microsoft-style employee profiles and self-service, Jira-style ticket/task management, Excel/Google Sheets-style workbooks, and other internal systems where technically possible.

Do not assume that every external system has an available API. Where a real integration is not currently possible, create a clean integration interface or connector architecture without inventing an API.

Goal

Transform the existing PTF/Gunda tool into a unified internal company operations platform where different departments can work inside their own controlled spaces while still collaborating.

Core concept:

One employee record + multiple department workspaces + shared tasks/tickets + controlled access + interconnected workflows + workbook-style data management.

The tool should feel like a combination of Microsoft/Entra identity, SharePoint, Power Apps, Jira, Excel/Google Sheets, internal HR/recruitment systems, internal scheduling systems, and existing PTF/Gunda functionality.

This is NOT a request to create fake copies of these products. Reproduce the useful workflows and user experience needed by the company inside the existing tool.

1. Preserve the Existing Tool

Before changing anything:

- Inspect the existing application and architecture.
- Identify current data structures, departments, workspaces, employee records, tasks, workbook/grid functionality, permissions, roles, backups, restore, audit, and local storage.
- Identify existing onboarding, workshop, performance, FMD, appearance, ID, logbook, and other modules.

Then extend the existing architecture.

Critical requirements:

- Do not unnecessarily rewrite working modules.
- Do not replace existing functionality simply because a different implementation is easier.
- Do not remove existing features.
- Do not reset existing data structures unless absolutely necessary.
- Do not create duplicate employee databases when the existing employee/person structure can be extended.
- Do not create duplicate task systems when the existing task functionality can be expanded.
- Do not create separate unrelated databases for each department.
- Make the platform more connected, not more fragmented.

3. Role-Based Access

Access must be based on role and department.

Employees should see only employee-facing information such as their profile, evaluations, scores, procedural mistakes, retraining targets, relevant training information, personal schedule, and authorized personal tasks/requests.

Employees must not see other employees' confidential information, HR recruitment information, manager-only information, confidential evaluation notes, HR records, or private department boards.

Managers / Shift Managers should have appropriate access to employee profiles, evaluations, re-evaluation requests, performance information, team information, requests, and tasks.

Performance Coaches should have access to evaluations, re-evaluations, performance records, procedural mistakes, retraining, assigned performance tasks, and relevant employee information.

HR should have access to employee lifecycle, recruitment, hiring information, termination workflows, HR tasks, required department notifications, and appropriate employee records.

Recruiting should have access to candidates, interview workbooks, candidate evaluations, interview comments, hiring decisions, recruitment pipeline, and recruitment tasks.

Appearance should have access to uniform inventory, assignments, returns, missing uniforms, employee uniform records, and related termination tasks.

FMD/Scheduling should have access to scheduling, shifts, rotation, attendance, access/presence information, team assignments, labour rules, and related tasks.

The architecture must allow additional departments to be added without rebuilding the system.

7. Inter-Department Workflow

This is one of the most important requirements.

Departments must be able to automatically create and exchange tasks.

Example: Employee Termination.

When an employee is being terminated, HR starts the termination process. The system can generate related tasks for:

HR:
- Process termination

Appearance:
- Collect uniform
- Confirm uniform returned

Fingerprint / Access:
- Remove building/fingerprint access

FMD:
- Remove employee from future schedules where appropriate

IT:
- Remove or disable required access where applicable

Management:
- Complete management actions

Each department receives its own task, while all tasks remain connected to the same employee termination process.

Use a parent process such as:

Employee Termination Case

with linked child tasks:

- HR Task
- Appearance Task
- Access Task
- FMD Task
- IT Task
- Management Task

Maintain a clear audit trail.

8. Department Comments and Exceptions

Departments must be able to communicate through tickets.

If the uniform was not returned, Appearance should be able to:

- Mark the uniform as missing
- Add the reason
- Attach relevant information
- Change task status
- Escalate if required

Example comment:

"Uniform was not returned."

This information must remain attached to the termination workflow and visible to authorized HR/users.

The same principle must work across departments.

35. Most Important Design Principle

Think of this application as a company operating system, not a collection of unrelated pages.

The employee is the central object.

Departments are connected through workflows.

Tickets/tasks connect departments.

Workbooks handle processes that genuinely benefit from spreadsheet-style work.

Dashboards show relevant information.

External systems provide data through controlled connectors.

Microsoft/SharePoint/Power Apps/Jira should be treated as systems this platform can integrate with, not as reasons to rebuild the entire application.

The final result should be:

One platform → one employee record → multiple departments → shared workflows → controlled access → connected tasks → reusable workbooks → external integrations.

Before making major architectural changes, inspect the existing code and identify what can be reused. Prefer extension and refactoring over replacement.

When you encounter an existing feature that already solves part of the requirement, reuse it.

When a requested feature conflicts with an existing implementation, explain the conflict and propose the smallest safe architectural change.

Do not invent technical capabilities that are not present.

Do not silently remove existing functionality.

Do not create fake integrations.

Build the system progressively, safely, and in a way that can eventually operate alongside the company's real Microsoft and internal systems.
